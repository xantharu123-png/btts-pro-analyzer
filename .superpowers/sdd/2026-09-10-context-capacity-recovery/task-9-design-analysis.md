# Task 9 design analysis: one owning physical/source traversal

Date: 2026-09-11. Read-only diagnosis against `07d975fb54a62ecb976c8040823e16fe45d9f16f`; only this report is authored. No implementation, tests, index, commit, SSH, or subagents.

## Decision

There is no defensible material fix inside the literal Task8 frozen file/function scope. Its projection works: all26 original queries hit, zero owned-full fallbacks, and the 42,099-row fold costs only0.733CPU. Another projection adjustment does not address the failure.

The smallest proposal with a plausible *material* saving is a new, explicitly approved D4 checking task: a **fixed owning physical-plus-Tennis traversal, with same-invocation reuse of B1 checks and complete source-specific checks, writing optional evidence directly into the existing accounted encoded pool**. Keep the independent encoded-row cold seal and every original/snapshot calculation. This is not permission to implement it; it requires a controller scope/proof amendment first.

Do not implement traversal fusion alone on the assumption it saves the entire87.302CPU cold phase. It does not. Do not bundle unrelated JSON/normalization rewrites. The proposal removes two identified repeated operations together: the second eligible physical decode/traversal, and the selected validator's repeated generic B1 normalization/hash checks on that very same freshly decoded row. Physical proof alone remains insufficient for any source or completeness authority.

## Same-owner opportunity examined first

Task7 already made `_validate_selected_tennis_receipt_cold` normalize actual content once and reuse `content_bytes` for its hash. Its remaining normalized-content and expected-native-envelope canonical comparisons are distinct checks, not disposable duplicates. Workload payload validation does not duplicate the generic closed B1 contract. `_store_encoded` independently validates freshly decoded encoded rows; removing that seal is forbidden and unsound for arbitrary direct `_store` inputs.

One genuinely narrow duplicate exists in `context_observations._decode_receipt`: `_decode_object(payload)` already proves canonical_bytes(content)==payload, then the caller encodes content again for normalized equality and again via digest(content). Within that same non-yielding call, comparing payload against canonical_bytes(normalized) and hashing payload would remove two serializations without a caller flag. All original decode/type/canonical/normalization/hash/index checks and their ordering can remain. But this is a **generic physical owner edit outside Task8**, and the profile's entire serialization time includes indispensable encodings too. It is not evidence for the roughly tens-of-seconds margin needed. Do not make it the release strategy or claim it closes the gap. It can remain excluded from the larger proposal; unchanged `_decode_receipt` is sufficient below.

Combining physical and source validation only in the later cold scan would remove repeated selected generic work but retain the whole second physical traversal. Combining traversals while retaining the whole selected generic validator removes the second traversal but leaves the other measured duplication. The proposed fixed co-owner addresses both with one provenance argument. There is no model/result cache.

The planner reads each original's actual persisted creation timestamp internally and calls the existing full publication validator. - The fixed coordinator lives with the existing cache/Tennis checking owner, not as another cache. It owns bounded planning, pending encoded bytes, source-failure cancellation, and eventual publication. Existing originals receive the optional cache through the fixed runtime orchestration; a passed cache object by itself is never completeness evidence.
- A narrowly factored source-internal residual validator receives only the freshly decoded row within the fixed owning call frame. It returns normal row data, never a proof capability. It is not a replacement public selected validator. The fixed coordinator itself invokes unchanged `_decode_receipt(raw)` before this residual helper, with no yield/callback/return of the decoded object between physical proof and source checking. Arbitrary direct calls to the residual helper cannot publish cache authority.
- The generic physical pass should use one shared fixed implementation, not a copied second decoder/check routine. Its complete content phase, full receipt phase, orphan check and final inventory stamp remain authoritative. A fixed coordinator branch is allowed only in the new entry point. Existing `validate_all()` callers get existing behavior and no Tennis cache. If physical validation already completed before this new call, there are no retained row proofs: use the existing postphysical cold preparation, never fabricate source coverage.

The unavoidable product scope is `context_runtime_inventory.py`, the observation/original orchestration in `context_runtime.py`, `context_runtime_tennis.py`, `context_runtime_history_cache.py`, and a small factoring in `context_sources/tennis_status.py`. `context_sources/tennis.py`, `context_observations.py`, generic contracts, transaction/input modules, v3/v2/math/CODE_PATHS, features/transport, schemas and deployment code need not change. ## Physical proof is not source proof

For an ordinary raw receipt, unchanged `_decode_receipt` already verifies: strict/canonical JSON, exact closed B1 content and nested JSON types, normalized equality, receipt/content hashes, canonical receipt clock and every outer index binding. Its output is fresh ordinary JSON owned solely by this invocation. No arbitrary caller object or subclass enters the optimized branch.

Immediately after that successful call, and only for an eligible known Tennis schema, the fixed source owner must still perform:

1. Exact ESPN/tennis source/sport checks, and schema discrimination.
2. For status: the complete existing `_validate_tennis_status_payload` (native IDs/tour/players, status flags/codes, schedule, issues, workload references and competition-reception identity), then full canonical expected-envelope equality using `_record_fields` against the canonical content bytes already bound to this receipt. Those bytes are the current raw row's payload, not caller-supplied proof from an earlier call.
3. For workload: exact kind/format checks and unchanged `validate_workload_record`, including its full payload numeric/time/bilateral/native binding contract.
4. Construct the exact selected evidence fields as existing selection does: prospective, effective_at=observed_at, publication_resolution=None. These are owner-generated literals; no caller-supplied evidence fields are trusted.

Thus only B1 predicates already proved on these identical owned bytes disappear from the *second* source invocation. Every source-specific predicate remains. The public `select_tennis_observations`, standalone native validator, public selected validator and `_validate_selected_tennis_receipt_cold` still cold-validate arbitrary inputs exactly; the independent cache seal calls that complete cold validator on `json.loads(encoded)` and cannot use the residual helper.

This factoring needs a line-by-line predicate/error matrix and differential tests. If maintaining the residual branch means copying source logic that may drift, factor the shared source-tail logic from the ordinary cold validator while preserving its generic-prefix checks and public behavior. Do not substitute Python dict equality for canonical equality: signed zero, booleans/numbers and strict types matter.

## Eligibility, ordering, and complete evidence

Plan both actual maximum tour cutoffs from all originals, including orphans and excess-query publications. Queries remain bounded to existing30 optional records/32aggregate slots. No new event/participant/latest pruning.

The complete physical pass still decodes **every** ordinary receipt, including future/unrelated/opposite-tour/inactive/unreferenced rows, and keeps protected final bodies opaque. After each successful physical decode, source checking is eligible exactly for known Tennis schemas at or before the maximum of the internally planned tour cutoffs. This union is equivalent to source validation required by the existing per-tour builders: each builder validates both tours before selecting its requested tour. The row enters only its actual tour's basis and only if it is within that tour's own maximum cutoff. Unknown schemas are not silently reclassified as Tennis. Opaque finals never enter source checking.

Build each basis in `(observed_at,digest)` order. The smallest bounded option is adding this explicit order to the **physical receipt query only**, while retaining the complete unfiltered LEFT JOIN and every row check. SQL traversal order within this phase was already explicitly unspecified by the fourth recovery refinement; content-before-receipt-before-orphan order is not optional. The new ORDER BY is itself an explicit amendment and must be measured for SQLite sort memory/CPU under AS2GiB. No index/schema/temp persistent object is added. If ORDER BY is not approved, sorting needs a separately designed and charged bounded representation; do not hide a per-row key/index list in Python or decode a second full inventory to sort.

No source completion is published until all physical/content/orphan/final-stamp checks succeed, all eligible source work succeeds, all retained encoded rows receive the independent complete cold seal, and the final mapping/generation/changes/main+temp proof and exact entry serial agree. The coordinator's actual unfiltered traversal completion supplies completeness; a generic physical stamp or row seal alone still does not.

## Failure/admission order and fallback

Planning is now speculative before physical completion, unlike Task8; this phase change needs explicit approval. To preserve existing error precedence, a planning-domain validation failure cancels optional preparation, releases its state, and lets complete physical validation run. After physical success, the ordinary existing postphysical planning executes and produces its usual error. No exception object/traceback is retained, avoiding hidden references to entire publications.

Likewise, a **source-specific domain validation failure** after a successful physical decode cancels all optional preparation and releases pending evidence immediately. Continue all physical checks. After successful physical validation, run the existing complete postphysical cold owner; it necessarily revisits source validation and emits the established error in its established per-tour order. Do not convert a failed source check into successful absence, continue using another tour's partial cache, or silently return a clean report. This fallback is error deferral, not source-error suppression. Test it with both valid physical data and later independent physical corruption.

Do not catch arbitrary BaseException as an optimization miss: interrupts, MemoryError/resource exhaustion, transaction/schema/closure/revocation failures and unexpected exceptions propagate fail-closed with cleanup. Catch only the established deterministic source/planning domain errors in their narrow respective blocks; physical `_decode_receipt` errors must never be caught by the source deferral block. No stored exception args/traceback are needed. A later integrity mutation cannot be disguised as cancellation; all subsequent/final physical and cache lifetime checks remain.

Cache/query pressure, no originals, never-completed/foreign proof, cancellation and oversized optional basis yield the existing safe full cold route. Pending bytes are released before fallback, not after it. Full consumer history admission remains256MiB in sealed mode with existing argument/error semantics; the optional64MiB retention limit must never become an input rejection. Whole-prefix admission still precedes original missing/ambiguous-native rejection. Direct `_store` can mint neither owned-completeness nor projections, including after a successful physical pass.

## Accounting and lifetime

Use the same `_bytes + _pending_bytes` accounting for every pending encoded row, plan/query/draft and eventual marker; aggregate limit64MiB and32slots are unchanged. Both-tour pending construction shares this one budget. Cancel the optional preparation conservatively on inability to fit a complete basis; do not create uncharged spill lists or preserve partial entries. Existing queries remain lower priority than a fitting basis.

After physical completion, run the unchanged full independent seal over the **existing pending encoded rows**: decode one, run the full cold validator, fold the bounded original queries, release decoded work. Do not materialize a complete decoded basis merely to pass it through `_store_encoded` and retain a second encoded copy. Refactoring storage mechanics to seal already-owned pending bytes is an explicit cache amendment; it is not a waiver of the seal. Before/after each decode, final/empty completion and serial publication retain existing lifecycle checks.

Pending bytes remain charged while sealing/sorting/publication occurs. Transfer ownership into the retained entry atomically without double-counting or resetting a still-live pending pool. Clear aliases and worker-frame locals before decrementing charges, fallback, pressure or eviction. Reentrant operations cancel optional work and cannot steal/replace the pending pool. Entry replacement/eviction removes completeness and projections even for identical bytes; no descriptor, local iterator or error traceback retains evicted rows. No new stronger asynchronous-DDL guarantee is claimed beyond existing sequential boundaries.

Prephysical cache creation must not accidentally pin `proof=None` as usable source authority. The fixed operation can bind its final proof only once, after the entire physical completion with the exact original transaction/schema/change pins intact. Ordinary externally constructed caches and direct stores cannot take this transition. Root/reviewer must inspect that transition as a new trust boundary, not merely loosen `_check_selected_proof` globally.

## Expected savings and stop condition

Removed work: one extra eligible SQL traversal, its repeated physical JSON decode/normalization/hash/index work and validation-stamp calls; then repeated selected-generic normalization/JSON tree traversal/hash comparisons on the identical freshly decoded receipt. Retained work: every physical pass predicate, all native source/workload predicates, canonical selected-row retention, independent encoded source seal, all projections/native/predictors and all full snapshot feature/transport replays. This targets both major halves of the observed cold profile, not the26CPU independent seal or mandatory snapshots.

The measurements support a plausible material reduction, **not a promised number or a300-second pass**. Exact benefit depends on full-row mix, cache fit, sorting, new fixed-owner overhead and source-tail factoring. If root cannot approve the limited inventory/source/cache/orchestration ownership changes or reviewers cannot establish exact residual-source proof plus mandatory fallback, conclude **no safe path within current authority**. Do not replace these obligations with trusted flags, source-error suppression, larger caps, pruned history, removed seal, changed feature/math code or old-hash whitelists.
