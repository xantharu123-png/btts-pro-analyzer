## Implementation

- `build_live_training_cases(path, requests, *, config, as_of, seconds=45)` accepts 1..100 explicit list/tuple requests with exactly `original_ref`, `outcome_ref`, and `identity_ref`; copies/fixes requests before opening one actual existing `dataset._reader` transaction; returns the complete unpublished tuple only after success.
- `_TennisBatchDiscovery` is local to that connection and call. One streamed SQL discovery groups only existing ESPN status/workload receipts received by the largest requested cutoff, before source JSON is touched. It projects only small tour/player/opponent/participant metadata once per distinct eligible content/event identity; Python intersects that one projection with requested `(tour, player)` identities. No requested-player SQL join repeatedly parses source JSON, and no full source bodies/inventory are copied or spooled in Python.
- Membership retains earliest actual matching receipt clock per `(tour, player, outer event_key)`. Each case admits only membership established by its own decision. Its target and every status/workload revision of every admitted key up to that decision are physically decoded and natively validated. Later participant removals and simultaneous conflicting revisions remain present. ATP and WTA are separately keyed.
- Actual production readiness now calls `iter_live_tennis_features` on the same connection. The previous content-only coarse index that could promote future association into an earlier decision is removed. Inventory-only returns before discovery/features and remains non-qualifying.
- `PreparedTennisHistory` validates each selected row and retains the full encoded selected history with exact chronological `(observed_at, digest)` order. Each feature scope closes before yielding to a consumer, including when a consumer aborts or retains a traceback. No validation flag/cache is accepted from a caller; no mutable prepared owner is reused across cases. Production consumers drop the yielded owner/history/features before preparing another case.
- `_TennisBatchBudget` covers original/config preparation, discovery, all cases and final result with one 1..600-second deadline. SQL interruption is owned and translated to timeout only when this deadline requested it. Default new-batch limit is 45 seconds.
- The unchanged `context_runtime.MAX_TENNIS_HISTORY_BYTES` (256 MiB) bounds combined conservatively charged lookup/request/origin metadata, one encoded selected history and required unpublished returned-case encodings. Physical selected COUNT/SUM(LENGTH(payload)) admission happens before loading selected bodies. The completed case output is charged cumulatively instead of renewing a whole limit per case. This is encoded/Python admission accounting, not a total-process RSS guarantee; native RSS belongs to the controller's probe.
- Approved lower-only private diagnostic profile: `_TennisBatchBudget(seconds=45, started=STARTED, selected_count=512, selected_bytes_per_case=2*1024*1024, selected_bytes_total=8*1024*1024)`. `selected_payload_bytes` is current-case actual physical payload length; `selected_payload_bytes_total` is cumulative and never renewed. External borrowed-reader diagnostics must install `budget.sql_progress` and clear it in their owning reader's `finally`, as the actual training and readiness readers already do.
- Outcomes are absent from discovery and the feature iterator. The normal training builder continues to use the existing physical original/state/identity/outcome owners, including existing later outcome clocks and unchanged `ReplayUnavailable` handling. No labels are loaded during originals/discovery preflight.
