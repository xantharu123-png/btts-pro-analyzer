# Source readiness: Football absences/lineups/minutes and tennis workload/end time

Date: 2026-09-07
Scope: bounded read-only inspection for Task 8/B4 and Task 10/B6. This is preparation only; it does not complete either task and makes no claim about a numerical model effect.

The binding standard is that retrieval time is not match end, publication time, or confirmed availability (`docs/superpowers/specs/2026-09-07-kontextmodell-design.md:86-94`). Football needs match-level appearances, starts, minutes and roles (`...kontextmodell-design.md:190-195`); tennis needs independently covered sets, games, duration, actual timing and result observation (`...kontextmodell-design.md:207-218`). Provider fields must be verified with bounded real responses before assumptions are encoded (`...kontextmodell-design.md:245-253`).

## Football — verified in current code

- `ChallengeDataProvider` uses API-Football at `https://v3.football.api-sports.io` and sends all calls through the atomic quota governor (`challenge_15k.py:682-720`; `api_budget.py:572-606`). `_football_get` returns only the decoded `response` list, discarding response metadata after the budget layer reconciles headers (`challenge_15k.py:721-751`; `api_budget.py:597-606`).
- Current source calls are `GET /fixtures` for scheduled/finished fixtures (`challenge_15k.py:753-807`), `GET /leagues?id=<league>&season=<season>` for declared injury/lineup coverage (`challenge_15k.py:1016-1051`), batched `GET /injuries?ids=...` with per-fixture fallback (`challenge_15k.py:1060-1108`), and batched `GET /fixtures?ids=...` with per-fixture fallback for details including the assumed nested `lineups` (`challenge_15k.py:1123-1171`, `challenge_15k.py:2683-2695`). `GET /fixtures/statistics?fixture=...` is explicitly team-level count-market settlement data, not player appearances (`challenge_15k.py:1173-1197`). There is no current player-appearance/minutes endpoint or adapter on this call path.
- Injury identity is fixture-validated at ingestion, then parsed as native `team.id` plus `player.id`; a non-empty player name is accepted as a fallback identity (`challenge_15k.py:1079-1107`, `challenge_engine.py:2380-2416`). `player.type` is reduced to `questionable` only when it contains “question”; every other value becomes `missing`, so confirmed absent vs suspended vs other statuses are not preserved, and “available” is not represented (`challenge_engine.py:2417-2421`). A free `material_impact` object currently controls only veto/assessment reporting and is not a learned effect (`challenge_engine.py:2422-2477`).
- Lineup validation uses native team IDs and 11 distinct positive native starter player IDs (`challenge_engine.py:2580-2622`). The display projection keeps only formation, coach name and starter names; it drops player IDs, bench/substitution data, roles/positions and all minutes (`challenge_engine.py:2625-2685`). Tests cover the synthetic native team/player-ID shape and reject partial/duplicate/wrong-team lineups (`tests/test_challenge_15k.py:4291-4329`), but do not prove a current provider response shape.
- Football history is team-result history. Football-Data CSV rows get pseudo fixture/team IDs where they cannot be joined to current native teams (`football_data_history.py:95-105`, `football_data_history.py:191-296`); the API tail contains native fixture/team IDs but still no player appearances (`football_data_history.py:354-447`). The base goal model selects last 12 venue and last 6 overall team matches and combines them 75/25 (`challenge_engine.py:860-904`, `challenge_engine.py:1090-1123`), but does not expose the per-event/component `reference_weights` needed to reconstruct the actual reference roster.

### Football readiness gaps

1. No measured match-level `player_id/team_id/fixture_id + minutes + started + role + performance`; consequently no aligned reference minutes, expected replacement minutes, participation training pairs, or regulation-vs-extra-time exposure.
2. No append-only raw injury/lineup revisions or provider publication time. Foreground `context_checked_at` is one timestamp captured after injuries, details, H2H and weather calls (`challenge_15k.py:2614-2644`); targeted refresh captures `checked_at` before those calls (`challenge_15k.py:2872-2906`). Neither is the per-response receipt time required by B1.
3. Current injury classification loses source status detail; current lineup normalization proves only complete starters. Corrected lineups, bench/role, uncertain participation, and complete-squad coverage remain unsupported.
4. **Provider capability assumption, not code fact:** API-Football may expose match-level player statistics (commonly documented under a fixture-player endpoint), but current entitlement, competitions, native joins, minutes/start/role semantics, pagination/completeness, timestamps and historical reach are unverified until the bounded probe.

## Tennis — verified in current code

- The current fixture/result sources are one daily SofaScore page, `https://api.sofascore.com/api/v1/sport/tennis/scheduled-events/{date}` (`scripts/tennis_daily.py:165-198`, `scripts/tennis_daily.py:259-268`), with ESPN fallback, `https://site.api.espn.com/apis/site/v2/sports/tennis/{atp|wta}/scoreboard?dates=YYYYMMDD&limit=400` (`scripts/tennis_daily.py:201-255`, `scripts/tennis_daily.py:358-364`). Results are fetched only for the exact stored fixture source and cached once per source/date/tour inside a settlement run (`scripts/tennis_daily.py:473-506`). These direct requests do not use the football quota governor or a persistent tennis request ledger.
- Fixture normalization preserves source name, native event/competition ID as `provider_event_id`, scheduled start, tour and participant names (`scripts/tennis_daily.py:170-196`, `scripts/tennis_daily.py:204-240`). It does not preserve native player IDs or tournament/tour IDs. Tests prove this parser contract for synthetic SofaScore and ESPN payloads (`tests/test_tennis_fixture_metadata.py:91-118`, `tests/test_tennis_fixture_metadata.py:276-309`), not live field availability.
- Normal-result parsing measures only winner/loser **set wins**: SofaScore reads `homeScore.current/awayScore.current`; ESPN counts set-line winner booleans (`scripts/tennis_daily.py:329-353`, `scripts/tennis_daily.py:432-468`). It emits no per-set game scores, total games, actual start, actual end or duration. Retirement/walkover are terminal classifications inferred from status/notes, but their winner and set counts are deliberately nulled and no retiring side is preserved (`scripts/tennis_daily.py:286-327`, `scripts/tennis_daily.py:370-430`). The associated tests confirm exactly those shapes (`tests/test_tennis_fixture_metadata.py:121-200`, `tests/test_tennis_fixture_metadata.py:313-401`).
- `result_observed_at` is genuine local UTC observation/receipt time captured after each daily page response, then persisted by settlement (`scripts/tennis_daily.py:259-268`, `scripts/tennis_daily.py:358-365`, `scripts/tennis_daily.py:532-574`; `tennis/shadow.py:945-1057`). It is not provider publication time or match end. The shadow schema can store optional `match_duration_minutes`, but the automatic parsers never emit `duration_minutes`, so automatic settlements persist it as null (`tennis/shadow.py:945-997`; `scripts/tennis_daily.py:564-574`).
- `observed_workload_context` accepts only settled, exactly name-matched, source+event-identified normal/retirement rows observed before cutoff (`tennis/workload.py:36-96`). It deduplicates by `(fixture_source, provider_event_id)`, totals sets and optional duration only over 7 days, and computes “minimum recovery” as decision cutoff minus result observation (`tennis/workload.py:97-123`). It has no games, 1/3-day windows, true end, exact recovery, next scheduled start in the recovery calculation, retirement-side evidence, availability/return report, or native player/tour namespace. Tests confirm five-set/duration behavior only with manually supplied synthetic duration and confirm future/walkover exclusion and event dedupe (`tests/test_tennis_prediction_revisions.py:287-338`).
- A separate ATP training adapter allowlists native match/tournament/player codes plus set wins, game wins and `match_duration` (`tennis/data_loader.py:55-120`), but joins matches only to tournament `start_dtm`/`tourney_date`, explicitly a conservative tournament-start cutoff (`tennis/data_loader.py:334-347`, `tennis/data_loader.py:398-480`). It is not wired into `workload_history`, and that date cannot prove match start/end or prospective availability. Field presence in the allowlist does not prove non-null coverage for the active years.

- Two real completed samples (both dated 2026-08-24) prove native match `competition.id`, native participant `competitors[].id` (not `athlete.id`), player display names, winner flags, and per-set `linescores[].value` with optional `tiebreak`. The current parser preserves the match ID and names but counts only line-winner booleans, so it currently discards the measured player IDs, game scores and tiebreaks (`scripts/tennis_daily.py:404-468`).
- In both samples `competitors[].statistics` is empty and the competition keys contain no match end or duration field. `competition.date == competition.startDate`; neither is proven actual start. The top-level event's `endDate` is tournament-level and must not be used as match end. `format.regulation.periods` is `5` even for 2:0 qualifying finals, so it is not safe evidence of the played or scheduled best-of format. No further Tennis source call is needed for this probe.
- These samples establish recoverable set-game workload and collision-safe ESPN participant IDs for the sampled payload shape, but **not** duration/minutes, exact recovery, actual start/end, retirement-side/availability evidence, fresh prospective coverage, ATP/WTA-wide completeness, or historical observation-at-cutoff coverage.

### Tennis readiness gaps

1. The prospective shadow path has reliable source/event identity, scheduled start, terminal class, set wins and actual result-observation time. The measured ESPN payload also supplies participant IDs and set-game values, but the parser drops them. Automatic duration, actual start/end, retirement side and availability remain absent.
2. Exact rest cannot be computed. Current “minimum recovery” ends at model decision time rather than scheduled next start, while `result_observed_at` is only a lower-bound anchor; historical tournament dates cannot repair this.
3. Retirement workload is currently lost with nulled sets/duration, walkovers are correctly excluded, and name matching cannot satisfy the required collision-safe ATP/WTA player namespace.
4. **Remaining provider capability assumption, not measured fact:** SofaScore's corresponding field shape remains unresolved because the single bounded request returned 403. ESPN now proves set-game and participant-ID fields for two samples, but no actual end-time/duration field; wider tour/date/retirement coverage remains unverified.
